# AIAgent Agent 设计复评报告

> 评估日期：2026-07-15  
> 评估对象：当前工作树，重点检查 TEXT 主运行链、Context、ToolGroup、工具执行、安全确认、记忆与请求控制  
> 对照基线：`docs/overview/agent-architecture-and-runtime-flow-evaluation.md`  
> 评估性质：架构与 Agent 行为逻辑复评，不是逐文件代码缺陷扫描

## 1. 执行结论

这轮改进是有效的，而且不是只补了文档或元数据。上一轮三个 P0 问题已经进入真实 TEXT 运行链；此前最主要的 P1——长上下文恢复——也已经在代码和自动化测试层面形成闭环。

当前项目已经是一套完成度较高的“车载领域约束型 Agent”：它不是单纯把 LangChain4j 接到大模型，而是用自研 Runtime、Context、ToolGroup、Safety、Memory 和 Trace 构造了可控的 Agent 执行外壳。对于 Demo 和内部联调，这条路线合理，且很有项目辨识度。

不过，项目还没有达到“真实车辆控制可放心交付”的程度。主要差距已经不再是模块缺失，而是动作链的最后三道语义边界：

1. 模型本轮可见的工具，还没有在实际分发时再次作为授权白名单核验；
2. Java 方法正常返回，不等于车辆动作真正成功，当前仍可能把业务拒绝识别成分发成功；
3. 最终自然语言答复没有被动作证据约束，模型仍可能在未执行或执行失败后声称“已经完成”。

因此，本轮总体判断为：

| 评估项 | 当前评分 | 判断 |
|---|---:|---|
| 总体架构设计 | 8.4 / 10 | 分层清晰，自研核心边界明确，复杂度基本有业务依据 |
| TEXT Demo 完成度 | 8.8 / 10 | 主链、上下文、取消、超时、安全确认均已成型 |
| 内部试用准备度 | 8.0 / 10 | 可进入系统化场景验收，但行为评测仍偏薄 |
| 真实车控准备度 | 6.3 / 10 | 需补执行授权、调用方身份、动作回执和结果真实性 |

与上一版相比，Demo 和内部试用能力均有明显提升；真实车控评分没有同步大幅提高，因为 Context 完整性不能代替控制权限与动作结果闭环。

结论：上一轮列出的三个 P0 已经完成，长上下文 P1 也基本完成；剩余工作已从“工程组件补齐”转向“动作语义和产品边界闭环”。

## 3. 当前 Agent 的真实设计定位

当前 AIAgent 更准确的定位不是“通用自主 Agent”，而是：

> 运行在 Android 车机后台、通过 AIDL 对外提供能力、由确定性控制面约束模型决策的车载领域 Agent 引擎。

它同时包含 Workflow 和 Agent 两种成分：

- 请求准入、意图路由、ToolGroup、Context 策略、安全检查、截止时间和终态抢占由代码确定；
- 模型在本轮被允许的工具空间内，自主决定是否调用工具、参数是什么以及是否继续循环；
- 每轮工具结果重新进入消息历史，形成“模型判断—环境反馈—继续判断”的 Agent 循环。

这与常见 Agent 设计原则是一致的：对边界清晰的业务采用可预测 Workflow，对需要语言理解和工具选择的部分保留模型决策空间。Anthropic 的 Agent 架构建议也强调简单、可组合的模式、环境真实反馈与停止条件，而不是为了“更像 Agent”增加不必要的自治层级：[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)。

### 当前 TEXT 主链

```text
AIDL 请求
  → 请求准入 / 去重 / 截止时间 / 取消注册
  → RequestSession 身份快照
  → IntentRouter
  → ToolGroupSelector（失败关闭）
  → ContextOrchestrator
       ├─ 11 个 Provider + 会话摘要
       ├─ 信任 / 可见性 / 优先级 / 生命周期策略
       └─ 超预算裁剪 → 记忆压缩 → CAS 写回 → 重组装
  → TextAgentLoopOrchestrator
       ├─ 模型调用
       ├─ Safety 检查
       ├─ 高风险确认
       ├─ ToolRegistry / ToolDispatcher
       └─ 工具结果回灌并继续迭代
  → 后处理 / 记忆写入 / 结果映射
  → CAS 唯一终态回调
```

这个流程的优点是“模型负责理解和选择，系统负责边界和状态”。这是当前项目最核心的架构价值。

## 4. 设计优点

### 4.1 自研控制外壳边界清晰

项目使用 LangChain4j 的消息、模型和 Tool Calling 能力，但真正编排请求的是自研 `AgentRuntime`、`ContextOrchestrator` 和 Agent Loop。这样既复用了成熟 API，又没有把车控安全、会话隔离和 Android 生命周期隐藏在框架内部。

### 4.2 Context 已成为独立系统，而不是 Prompt 字符串拼接

当前 Context 具备来源注册、信任标记、模型可见性、按请求/按迭代生命周期、优先级裁剪、Token 预算和记忆压缩恢复。尤其是工具结果和动态车辆状态能够在下一轮重新采集，这比“请求开始时拼一次 Prompt”更符合真实 Agent 循环。

### 4.3 工具治理与业务领域结合紧密

当前代码实际包含 46 个 `@Tool` 声明、13 个 ToolGroup。系统先做轻量意图识别，再只暴露相关工具，能够降低模型选择难度、Token 消耗和误调用面。反射式 Registry/Dispatcher 又避免了为每个工具重复编写调度样板。

### 4.4 请求可靠性设计明显强于普通 Demo

单槽准入、重复请求治理、30 秒 Deadline、底层网络取消、终态 CAS、完成态短期缓存等机制，使“用户取消了但模型仍继续执行”“超时和成功同时回调”等常见 Agent 竞态得到了系统性处理。

### 4.5 安全不是一个布尔开关

项目已经形成安全规则、风险动作确认、确认超时、确认前状态重检、原子消费和虚拟状态机。即使当前仍属于 Demo 级，这套骨架比单纯依赖系统提示词更可靠，也为接入真实车辆状态和策略引擎预留了合理位置。

### 4.6 记忆和可观测性是主链能力

Session、长期用户记忆、提取、压缩、完整历史持久化与 ToolExchange 完整性共同构成了较完整的记忆体系；OpenTelemetry/Phoenix Trace 覆盖请求、模型、工具和上下文，使 Agent 的多轮决策不再是黑盒。

## 5. 仍需补齐的 Agent 逻辑

以下内容按“影响 Agent 行为正确性”排序，不按代码缺陷数量排序。

### 5.1 P0（接入真实车控前）：把工具可见性升级为执行授权

当前 ToolGroup 决定了本轮发送给模型的 `requestTools`，但模型返回 `ToolExecutionRequest` 后，主循环直接进入 Safety 和全局 `ToolRegistry.dispatchWithOutcome()`。分发器会接受任何已注册工具，尚未重新核验该工具是否属于本轮 ToolGroup。

这意味着“没有展示给模型”只是降低其调用概率，并不是安全边界。对于模型异常输出、协议注入或未来框架行为变化，仍应在分发前执行：

```text
toolName ∈ 本轮授权工具集合
且 operationMode 允许写操作
且 toolPolicy 允许当前调用方、车辆状态和风险级别
```

不满足任一条件都应失败关闭，并生成结构化拒绝结果。

### 5.2 P0（接入真实车控前）：建立“动作回执”，不要把方法返回等同于业务成功

`ToolDispatchOutcome` 已能说明反射方法是否成功调用，却不能说明车控动作是否完成。例如虚拟状态机在车门未关闭、参数越界等情况下可能正常返回一段失败文本；从 Java 调用层看它仍然是 `dispatchSuccess=true`。

建议引入统一动作结果，至少包含：

- `status`：`APPLIED / REJECTED / FAILED / PARTIAL / UNKNOWN`；
- `reasonCode` 与可展示说明；
- `stateBefore`、`stateAfter` 或可验证的状态差异；
- `actionId`，用于确认、Trace、幂等和后续查询；
- 数据来源：虚拟状态、SOA 接收回执或车辆实际状态回读。

真实车控中，“请求已发送”也不能直接等于“车辆已执行”，应由实际回执或状态回读决定最终结论。

### 5.3 P0（接入真实车控前）：最终答复必须由执行证据约束

当前系统提示词要求模型不要虚报成功，但 `NoToolCallTerminator` 会接受任意普通模型文本，结果收集器也没有检查“成功表述”是否对应成功动作记录。因此模型仍可能未调用工具就回答“已经打开”，或在业务拒绝后回答“操作成功”。

建议增加结果真实性门：

- 对明确的写操作请求，只有 `APPLIED` 动作回执才允许生成“已完成”；
- 无工具调用时，只能说明未执行、需要澄清或当前无法操作；
- `REJECTED/FAILED/PARTIAL` 必须使用与结果一致的答复模板；
- 最终 `AgentResult` 保存结构化动作记录，而不是只保存工具名、参数和字符串结果。

这一项是 Agent 从“会调工具”进化到“能对任务结果负责”的关键。

### 5.4 P0（接入真实车控前）：绑定 AIDL 调用方身份和确认归属

`AIAgentService` 当前是 exported Service，Manifest 未看到服务级签名权限；运行链也未发现基于 Binder UID/包名的调用方校验。与此同时，`PendingToolAction` 主要绑定 session 和原请求，没有绑定真实调用方 UID、用户、客户端实例或授权主体。

风险不只是 Android 安全问题，也会破坏 Agent 的“谁发起、谁确认、谁接收结果”语义。建议：

- 使用签名级权限或可信包/证书白名单保护 AIDL；
- 在请求入口生成不可伪造的 caller identity；
- 待确认动作绑定 caller、user、session、request 和过期时间；
- 仅允许原调用方确认，并在确认时重新执行权限与状态检查。

### 5.5 P1：区分查询、控制和歧义请求

当前 Intent 主要识别车辆领域，例如空调、车窗、座椅，但没有把“查询状态”和“执行动作”作为强类型边界。“车窗现在开了多少”可能进入包含写工具的 WINDOW 组，系统主要依靠 Prompt 阻止误操作。

建议增加 `operationMode = QUERY / COMMAND / AMBIGUOUS`：

- QUERY 只暴露只读能力或直接使用可信车辆状态；
- COMMAND 才能进入写工具和 Safety；
- AMBIGUOUS 必须澄清，不能推断执行。

### 5.6 P1：处理复合意图和多动作的部分成功

关键词路由当前倾向选择一个最高优先级领域。对于“打开空调并关闭车窗”这类跨域指令，可能只覆盖一个 ToolGroup。即使模型获得多个调用，低/中风险动作也是顺序执行；第二个失败时，第一个可能已经生效，但系统缺少统一 `PARTIAL` 语义和补偿策略。

无需立即引入复杂通用 Planner。更适合当前项目的是确定性复合指令拆分：识别多个领域、生成受限动作列表、逐项 Safety、显式汇总每项结果；不能安全拆分时就澄清。

### 5.7 P1：统一工具级策略，避免风险元数据漂移

ToolGroup 中存在风险信息，Safety 又维护高风险工具集合和规则。如果将来新增高风险工具但漏配其中一处，可能被默认放行。建议建立唯一的 Tool Policy Registry，为每个写工具声明：所属组、读写属性、风险级别、确认策略、状态前置条件、允许调用方和结果类型，并在启动时校验 46 个工具是否完整覆盖。

### 5.8 P1：长期记忆提取不应阻塞已经准备好的用户答复

当前长期记忆提取位于 TEXT 响应完成前的主链中。它是有价值但非本次答复必需的副作用，可能继续消耗 Deadline、占用全局单槽，甚至使已经生成好的答复最终被超时终态覆盖。

建议在成功答复形成后先完成用户终态，再将记忆提取放入有界、可取消、可观测的后台队列；如果需要强一致性，也应设置独立短预算，失败不反转主请求结果。

### 5.9 P1：建立 Agent 行为评测，而不只依赖单元测试

354 个 JVM 测试证明模块行为和边界条件覆盖已经较好，但 Agent 的正确性还包括“是否选择了正确动作、是否产生正确状态变化、是否拒绝危险动作、是否诚实汇报”。建议建立固定行为集，至少覆盖：

| 维度 | 核心指标 |
|---|---|
| 任务结果 | 请求完成率、澄清正确率、状态变化正确率 |
| 决策轨迹 | ToolGroup 命中率、工具选择率、参数正确率、无关工具调用率 |
| 结果真实性 | 成功表述与动作回执一致率、虚假完成率 |
| 安全 | 越权拦截率、高风险确认绕过率、提示注入攻击成功率 |
| 可靠性 | 超时终止率、取消残留调用数、重复执行率、部分成功识别率 |
| 成本与体验 | P50/P95 延迟、模型轮数、Token、澄清轮数 |

Agent 评测应同时检查最终结果和执行轨迹，而不是只做文本相似度。可参考 Anthropic 的行为评测实践：[Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。

### 5.10 P2：逐步收敛双运行链和多模态旧路径

`AgentLoopOrchestrator` 与 `TextAgentLoopOrchestrator` 以及 TEXT/IMAGE/VOICE/CONTROL 的不同控制面会带来安全和错误语义漂移。当前不建议大规模重写；可以先抽取共享的“工具授权—Safety—执行—动作回执—Trace”管线，再按业务优先级迁移其他入口。

## 6. 建议的下一阶段顺序

### 第一组：动作可信闭环

1. 分发前执行本轮工具授权白名单；
2. 建立结构化 `ActionReceipt`；
3. 用动作回执约束最终答复和 `AgentResult`。

这三项应作为一个整体完成，因为它们共同回答：“模型有没有权限执行、动作实际有没有成功、Agent 能不能据此说成功。”

### 第二组：调用方与安全策略闭环

1. AIDL 签名权限或可信调用方校验；
2. 确认动作绑定 caller/user/session/request；
3. 统一 Tool Policy Registry，并启动时校验覆盖率。

### 第三组：能力和评测闭环

1. QUERY/COMMAND/AMBIGUOUS 分类；
2. 受限复合意图拆分与 `PARTIAL` 结果；
3. 长期记忆提取移出主响应关键路径；
4. 建立可重复运行的 Agent 行为基准集。

## 7. 项目特点与简历表达

### 7.1 项目最有辨识度的特点

1. **Android 车载后台 Agent，而非普通聊天应用**：无 UI 前台 Service，通过 AIDL 向 Launcher/SystemUI 等客户端提供对话、会话、取消和回调能力。
2. **自研 Agent 控制面**：基于 LangChain4j 的模型与 Tool Calling 原语，自研 Runtime、Context 和 Tool Loop，保持关键业务边界可控、可调试。
3. **上下文工程完整**：11 个 Provider、集中式策略、动态逐轮上下文、Token 预算、长对话压缩、CAS 防并发覆盖。
4. **领域化工具治理**：46 个工具、13 个 ToolGroup，通过意图路由缩小工具空间，并使用集中式反射注册和调度减少样板代码。
5. **车控可靠性与安全骨架**：请求准入、Deadline、底层取消、终态 CAS、高风险确认、状态重检和虚拟车辆状态机。
6. **记忆与可观测性一体化**：SQLite 会话/长期记忆、记忆提取与压缩，以及 OpenTelemetry + Phoenix 全链路追踪。

### 7.2 简历一句话版

## 9. 最终判断

这次迭代已经把 AIAgent 从“模块较完整的 Agent Demo”推进到“主运行链基本闭环的领域 Agent 引擎”。它最大的优点不是使用了多少框架，而是围绕车载约束建立了自己的 Context、工具治理、请求可靠性、安全和观测体系。
