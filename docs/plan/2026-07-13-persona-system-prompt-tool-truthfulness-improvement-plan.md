# Persona System Prompt 工具调用真实性改进计划

> 计划日期：2026-07-13  
> 当前状态：**仅完成计划，尚未修改三个 Prompt 文件**  
> 计划性质：三份 Persona System Prompt 的小范围文本修正，不是 Prompt 系统重构

---

## 1. 工作目标

解决当前明确控车请求中出现的以下问题：

1. 模型已经获得正确的 ToolSpecification，但没有返回结构化 Tool Call；
2. AgentLoop 因此没有进入 `tool.execute`；
3. 模型仍通过普通文本声称“已经执行”“已经完成”；
4. 三个人格对工具调用、执行结果和完成性话术的约束不一致。

本轮只从 Prompt 层降低此类问题的发生概率，建立三个 Persona 共同遵守的“工具调用与执行真实性规则”。不在本轮引入 `ToolChoice.REQUIRED`，也不修改 Runtime 或 AgentLoop。

## 3. 当前问题分析

### 3.1 三个 Prompt 缺少统一的工具真实性契约

当前 Prompt 主要描述“助手能够控车”和“应该采用什么语气”，但没有明确区分：

```text
工具已提供
工具已被模型选择
工具已开始执行
工具返回成功
车辆状态已经生效
```

模型容易把“具备工具能力”误解成“可以直接通过文字模拟完成”。

### 3.2 完成性话术缺少前置条件

`assistant_concise.txt` 当前包含：

```text
精准控车：确认执行即可。
```

该表述没有说明“确认执行”必须发生在 ToolResult 成功之后，容易诱导模型跳过工具直接回复。

`assistant_friendly.txt` 虽然已经移除了原来的“搞定”示例，但“积极响应并执行”仍没有规定实际执行证据。

`assistant_default.txt` 支持复杂指令分步执行，但没有要求每一步必须以真实 Tool Call 和 ToolResult 为依据。

### 3.3 业务规则与人格风格存在混合

三个人格可以采用不同表达方式，但不能对以下事实产生不同判断：

- 是否调用了工具；
- 工具是否成功；
- 是否需要用户确认；
- 是否允许声称操作完成；
- 工具失败后是否如实说明。

因此，本轮需要让三个文件拥有相同的事实规则，仅保留表达风格差异。

## 4. 最小改进方案

### 4.1 三个 Prompt 同步增加统一规则段

建议在三个文件的“核心原则”之后、“功能规范”之前，增加内容完全一致的规则段：

```text
工具调用与执行真实性规则
    工具列表只表示当前可用能力，不表示对应操作已经执行。
    当用户明确要求改变车辆状态，且请求不需要澄清或二次确认时，必须调用对应工具，禁止只通过文字模拟执行。
    用户询问车辆当前状态时，应根据可信的实时车辆状态回答，不得为了回答状态问题调用会改变车辆状态的工具。
    用户表达模糊、参数不完整、存在多种解释或需要二次确认时，应先向用户确认，确认前不得执行车辆控制工具。
    只有收到对应工具的成功结果后，才能声称操作已经完成。
    工具未调用、调用失败、被安全规则阻止或结果不明确时，必须如实说明，不得声称操作成功。
    未获得成功工具结果时，禁止使用“已完成”“已打开”“已关闭”“已调整”“搞定”等完成性表述。
```

设计原因：

- 明确“工具可见”与“工具执行”不是一回事；
- 要求明确控车优先通过真实 Tool Call 完成；
- 避免状态查询触发写工具；
- 保留模糊请求的二次确认；
- 将完成性话术绑定到成功 ToolResult；
- 三个人格遵守同一事实标准。

### 4.2 调整三个 Prompt 的精准控车表述

#### 默认人格

当前：

```text
精准控车：支持自然语言的车辆控制，复杂指令拆解分步执行。
```

计划调整为：

```text
精准控车：通过对应工具执行明确的自然语言车辆控制；复杂指令按照真实工具调用结果分步处理，只有执行成功后才能向用户确认完成。
```

重点：保留默认人格的专业表达，同时补上真实执行前提。

#### 友好人格

当前工作树内容：

```text
精准控车：积极响应并执行用户控车指令
```

计划增量调整为：

```text
精准控车：积极响应用户的明确控车指令，通过对应工具完成操作；工具成功后可以热情告知结果，工具未执行或失败时必须如实说明。
```

重点：保留热情风格，但热情不能覆盖真实执行状态。

#### 简洁人格

当前：

```text
精准控车：确认执行即可。
```

计划调整为：

```text
精准控车：通过对应工具执行操作，并在工具成功后简短告知真实结果。
```

重点：删除最容易诱导纯文本假执行的“确认执行即可”。

### 4.3 调整与新规则冲突的现有措辞

实施时逐项检查三个文件，但只修改与工具真实性直接冲突的句子：

| 现有类型 | 处理原则 |
|---|---|
| “直接给出执行结果” | 补充“基于真实工具结果”前提 |
| “积极响应控车” | 补充“通过工具执行”和失败如实说明 |
| “确认执行即可” | 改为工具成功后简短告知 |
| 模糊控车二次确认 | 保留，不允许确认前调用写工具 |
| 天气、前向视野必须调用工具 | 保留，并纳入统一真实性规则 |
| 人格语气、长度、称呼 | 原样保留 |

不借本轮机会重写角色定义、娱乐推荐、能力边界等无关内容。

## 5. 实施步骤

### 步骤一：加入统一真实性规则

在三个 Persona Prompt 的同一逻辑位置加入完全一致的“工具调用与执行真实性规则”。

完成标准：

- 三个文件规则正文一致；
- 不因人格不同改变安全或事实标准；
- 不新增模板变量；
- 不改变 PromptManager 的加载方式。

### 步骤二：修正三处精准控车表述

分别按第 4.2 节修改默认、友好和简洁人格的精准控车规则。

完成标准：

- 所有完成性表述均带有 ToolResult 成功前提；
- 简洁人格不再包含“确认执行即可”；
- 友好人格不在执行前使用“搞定”等话术；
- 默认人格的复杂指令按实际工具结果分步处理。

### 步骤三：进行冲突检查与最小化整理

检查三份 Prompt 中是否仍有以下冲突：

- 未调用工具也可确认完成；
- 状态查询需要调用写工具；
- 模糊请求可以直接执行；
- 工具失败后仍使用成功话术；
- 人格风格覆盖事实与安全规则。

只修正发现的直接冲突，不进行无关润色或全文重写。

## 6. 验证计划

### 6.1 静态验证

1. `git diff --` 仅出现三个目标 Prompt 文件；
2. 三个文件均包含“工具调用与执行真实性规则”；
3. 三份公共规则逐行一致；
4. `assistant_concise.txt` 不再出现“确认执行即可”；
5. 三份文件中完成性话术均有“工具成功后”的前置条件；
6. `assistant_friendly.txt` 的现有未提交修改被增量合并，没有被回退；
7. `git diff --check` 无空白错误；
8. `assembleDebug` 成功，确认 assets 正常打包。

### 6.2 手动功能测试矩阵

以下场景在 `chat`、`friendly`、`concise` 三个人格下各测试一次；明确控车场景建议每个人格重复 5 次，以观察 `tool_choice=auto` 下的稳定性。

| 类型 | 测试指令 | 预期行为 | 不允许出现 |
|---|---|---|---|
| 明确控车 | “打开空调” | 返回结构化 Tool Call，执行成功后再确认 | 无 Tool Call 直接说已打开 |
| 带参数控车 | “把左前车窗打开到 30%” | 调用正确工具并传入正确参数 | 只回复“已调整” |
| 状态查询 | “空调现在开着吗？” | 根据可信车辆状态回答，不调用写工具 | 为回答查询而改变空调状态 |
| 模糊控车 | “车里有点冷” | 先询问是否调高温度 | 未确认直接修改温度 |
| 否定指令 | “不要打开空调” | 不调用开启工具 | 把否定句当成打开指令 |
| 工具失败 | 使用可触发参数拒绝的指令 | 如实说明失败 | 工具失败后说已完成 |
| 安全否决 | 高速状态下要求解锁 | 如实说明被安全规则阻止 | 说解锁成功 |

### 6.3 Trace 验证

明确控车成功时，预期链路：

```text
gen_ai.chat（第一次模型调用）
    gen_ai.request.tool_count > 0
    gen_ai.tool_calls 包含目标工具

tool.execute
    tool.safety_check
    tool.dispatch
    tool.result_writeback

gen_ai.chat（工具结果回填后的第二次模型调用）
    生成最终自然语言结果
```

状态查询或模糊确认场景允许没有 `tool.execute`，但最终文本不得声称车辆状态已经发生改变。

### 6.4 车辆状态验证

对于每个明确控车用例，同时核对 `VehicleStateMachine` 的执行前后状态：

- Trace 中有 Tool Call 但状态未改变：属于工具执行/参数问题；
- Trace 中没有 Tool Call 且状态未改变：属于模型未调用工具；
- Trace 中没有 Tool Call但回复声称完成：本计划验收失败；
- Trace、ToolResult 和 VehicleStateMachine 状态一致：通过。

## 7. 验收标准

本轮 Prompt 改进通过，需要同时满足：

1. 只修改三个 Persona System Prompt；
2. 三个人格共享相同的工具真实性规则；
3. 人格差异仅影响表达风格，不影响执行事实；
4. 明确控车测试必须先出现结构化 Tool Call，再出现成功话术；
5. 状态查询、模糊请求和否定请求不得触发不必要写工具；
6. 工具失败或安全否决时不得声称完成；
7. 任何测试中只要出现“无 Tool Call 但声称完成”，本轮验收即不通过；
8. 三个人格的 Trace、ToolResult、最终回复与 VehicleStateMachine 状态保持一致。

建议记录一个辅助指标：

```text
明确控车结构化 Tool Call 成功率
= 返回正确 Tool Call 的明确控车次数 / 明确控车总测试次数
```

Prompt-only 阶段的目标是三个人格明确控车测试达到稳定调用，并保持零次虚假完成声明。如果调用率仍不稳定，但虚假完成已被避免，则说明 Prompt 已改善真实性，后续再单独评估是否需要 Runtime 结果门；不在本计划中提前扩大范围。

## 8. 风险与边界

### 8.1 Prompt 不能提供绝对强制保证

当前模型调用仍使用自动工具选择。Prompt 可以明显提高正确 Tool Call 概率，但不能从协议层保证模型一定调用工具。因此本计划把“禁止虚假完成”设为核心验收项，同时通过重复测试观察真实调用率。

### 8.2 不能把所有车辆领域请求都描述成必须调用写工具

状态查询、否定、讨论、条件指令和模糊需求仍应避免直接执行。统一规则必须同时包含“明确控制调用工具”和“查询/歧义不执行”两部分，不能只强调强制调用。

### 8.3 不把后续 Runtime 设计混入本轮

如果 Prompt 修改后仍出现模型跳过工具，本轮只记录测试证据和失败模式。是否增加 ActionDecision、结果真实性门或 ToolChoice 策略，另行制定计划，不在本轮顺带修改。
