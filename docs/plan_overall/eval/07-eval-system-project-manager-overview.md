# AIAgent Eval 系统计划汇报说明

> 文档定位：面向项目经理解释本轮三份 Eval 计划共同设计了什么系统、系统在做什么，以及三端如何协作。
>
> 本文只说明计划目标和系统设计，不评价当前代码完成度与验收状态。

## 1. 一句话说明

本轮计划要建立的是一套面向车载 AI Agent 的 Demo 级评估系统：它能够按照预先编写的测试案例，自动或半自动地向真实 AIAgent 发起请求，记录回答、车辆状态变化和完整运行轨迹，再使用规则检查与大模型评审生成可复核的评估结果和对比报告。

它解决的核心问题不是“Agent 能不能返回一句话”，而是：

- Agent 是否理解了用户意图；
- 是否选择并正确执行了工具；
- 是否遵守车辆控制和安全规则；
- 是否真正改变了预期的车辆状态；
- 运行流程、Trace 和最终结果是否完整一致；
- 新版本相较旧版本是否发生能力退化。

## 2. Eval 是什么

Eval 是 Evaluation（评估）的简称，可以理解为 Agent 的“标准化测试与质量检查系统”。

传统测试通常检查某个函数是否返回固定值，但 AI Agent 的输出具有一定开放性，不能只靠字符串完全相等来判断。因此，本 Eval 系统同时检查三类事实：

1. **最终结果事实**：Agent 最终向用户回复了什么，成功还是失败。
2. **环境状态事实**：执行前后车辆状态发生了什么变化，例如空调是否开启、温度是否调整到目标值。
3. **运行过程事实**：Agent 是否经过正确的 Context、模型、工具、安全审核和响应分发流程。

三类事实相互独立又能通过同一关联 ID 对齐，从而回答“结果对不对、过程对不对、车辆最终状态对不对”。

## 3. 为什么要引入这套系统

随着 AIAgent 的 Runtime、Context、Memory、Tool、Safety 和 Trace 等模块逐渐成型，仅靠人工聊天体验已经难以稳定判断一次改动是否影响了其他能力。

本轮 Eval 计划主要解决以下管理和研发问题：

- 把零散的人工测试整理成可重复执行的标准案例；
- 每次修改 Agent 后，用同一批案例重新验证；
- 将主观的“感觉效果不错”转化为有证据的评估结果；
- 发生失败时，能够通过 Trace 和状态快照定位失败环节；
- 保存不同版本的评估结果，用于版本横向比较和回归检查；
- 为未来扩展 RAG、视觉问答和更多车控能力保留统一评估基础。

## 4. 三份计划分别负责什么

三份计划共同组成一个系统，但分别作用于三个项目。

| 计划 | 所属项目 | 核心职责 | 可以理解为 |
|---|---|---|---|
| 电脑端 AIAgent_Eval 实现计划 | `AIAgent_Eval` | 管理测试案例、驱动执行、读取结果和 Trace、进行评分、生成报告 | 评估系统的大脑 |
| AIAgent Eval 适配计划 | `AIAgent` | 提供受控车辆环境、状态快照、Trace 关联和版本信息，并保证不改变正式 Agent 主链路 | 被测系统的测试接口与观测能力 |
| TestApp Eval Bridge 计划 | `AIAgentTestApp` | 在电脑端与 AIAgent 之间转发命令，调用真实 Agent，采集响应和状态并结构化落盘 | 连接电脑和车机 Agent 的桥梁 |

三端总体关系如下：

```text
测试案例与评分规则
        │
        ▼
AIAgent_Eval 电脑端评估程序
        │ 发送 EvalCommand / 读取 EvalResult
        ▼
AIAgentTestApp Eval Bridge
        │
        ├── 通过正式 AIDL 发送真实 AgentRequest
        │
        └── 通过 Debug Eval 接口准备和读取车辆环境
        ▼
AIAgent Runtime → Context → LLM → Tool → Safety → VehicleState
        │
        ├── AgentResponse
        ├── 车辆状态快照
        └── Phoenix Trace
        ▼
规则评分 + LLM Judge + Hard Gate + 版本对比报告
```

## 5. 电脑端 Eval 系统计划

电脑端项目是整个评估系统的统一入口，负责组织“测什么、怎么测、如何判定、怎样汇报”。

### 5.1 Dataset 测试案例

测试案例以结构化 Dataset 保存。每个案例描述：

- 用户输入；
- 用户、会话和 Persona；
- 测试前需要准备的车辆状态；
- 预期成功、失败、安全拒绝或二次确认等结果；
- 预期调用的工具；
- 预期车辆状态变化；
- 评分规则和必要的 Hard Gate。

除了单轮案例，还支持由多个步骤组成的 Scenario，例如“先发起高风险车控请求，再发送确认文本”。

### 5.2 三种执行方式

电脑端计划保留三种执行模式：

- **Fixture 模式**：使用固定样例离线验证评分、报告和系统逻辑，不依赖 Android 设备。
- **Manual 模式**：电脑生成命令，由开发人员在 TestApp 中人工确认执行，优先形成最小可靠闭环。
- **ADB 模式**：电脑通过 ADB 驱动同一个 TestApp 入口，实现 Demo 级自动运行。

三种方式使用同一套命令和结果协议，避免形成互不兼容的多套评估流程。

### 5.3 评分方式

评估采用分层方式，而不是完全交给大模型主观判断：

1. **确定性检查**：检查 ID、请求状态、工具名、车辆状态、Trace 完整性等明确事实。
2. **Hard Gate**：对安全性、协议完整性和关键行为设置不可被平均分掩盖的硬门槛。
3. **LLM Judge**：对回答质量、相关性、表达效果等难以用固定规则判断的部分进行补充评分。

Judge 模型通过配置选择，不与某一个模型供应商永久绑定。

### 5.4 评估产物

每次评估 Run 会保留：

- 使用的数据集和配置；
- 被测 Agent、Prompt、模型与协议版本；
- 每个 Case/Trial 的原始结果与标准化结果；
- 确定性评分、Hard Gate 和 Judge 结果；
- 失败原因与证据；
- 汇总报告；
- 基准版本与候选版本的差异比较。

因此，评估结果可以复查，而不只是输出一个无法解释的总分。

## 6. AIAgent 适配计划

AIAgent 仍然是被测对象。计划不会把 Dataset、评分器或报告系统塞进 Agent APK，而是只增加必要的 Debug/Test 适配能力。

### 6.1 可控车辆测试环境

AIAgent 为 Demo 虚拟车辆状态机增加：

- 8 个车辆子系统的结构化状态快照；
- 恢复默认状态；
- 原子应用状态 Patch；
- 状态修订号；
- 状态操作校验。

这样，每条案例都可以从确定的车辆状态开始，并在请求结束后验证实际状态变化。

### 6.2 Eval 环境租约

为了避免人工操作、主动场景或其他请求同时改变车辆状态，计划引入临时 Eval 环境租约：

- 同一时间只允许一个评估环境占用车辆状态；
- 非评估请求不能并发污染本轮状态；
- 租约具备超时释放能力；
- 内部 token 不进入电脑端结果、Prompt、Trace 或日志。

这一设计的作用是保证案例之间相互隔离，提高评估结果的可重复性。

### 6.3 真实主链路不变

正式 TEXT 请求仍经过现有：

```text
AIDL → AgentRuntime → Context → AgentLoop → LLM → Tool/Safety → AgentResponse
```

Eval 不绕过 Runtime，也不会直接调用某个 Tool 制造“测试成功”。因此测到的是 Agent 的真实综合能力，而不是旁路接口。

### 6.4 Trace 和版本证据

AIAgent 会补充稳定关联信息，使电脑端可以将以下内容对齐：

- TestApp 收到的 AgentResponse；
- 电脑端生成的 correlationId；
- AIAgent 的真实 requestId；
- Phoenix 中的根 Trace；
- 请求开始时的车辆环境 revision。

同时提供 APK、Prompt 摘要、模型、Trace 模式和状态 Schema 等版本指纹，避免不同版本的结果被误放在一起比较。

### 6.5 Debug 与 Release 隔离

车辆状态控制入口只存在于 Debug 构建，正式 Release 不暴露 Eval Debug Service。Eval 能力用于开发验证，不成为量产 App 的远程控制接口。

## 7. TestApp Bridge 计划

TestApp 是电脑端和 AIAgent 之间的 Android 桥接层。它既不负责评分，也不重新实现 Agent。

### 7.1 接收评估命令

TestApp 接收电脑端的结构化命令，包括：

- 获取和释放评估环境；
- 重置、应用和读取车辆状态；
- 创建、切换和删除会话；
- 发送 TEXT 请求；
- 取消指定请求；
- 读取版本信息。

每条命令拥有独立 correlationId，用于结果文件幂等和跨系统关联。

### 7.2 调用真实 AIAgent

对于用户问答，TestApp 继续通过现有正式 Facade/AIDL 构造 AgentRequest，并由 TestApp 生成真实 requestId。

电脑端只提供 correlationId，不直接控制 AIAgent 的 requestId，从而保持现有请求生命周期和取消机制不被破坏。

### 7.3 采集结构化结果

TestApp 将一次执行中的信息统一整理为 EvalResult：

- AgentResponse；
- operationResult；
- 请求前车辆状态；
- 请求后车辆状态；
- 版本指纹；
- 各阶段时间；
- 桥接错误。

结果采用单向状态：PENDING、RUNNING、TERMINAL。终态一旦写入，不允许被迟到回调或 watchdog 覆盖。

### 7.4 可靠结果通道

结果写入 TestApp Debug 专用结构化文件，由电脑端通过 ADB `run-as` 读取。Logcat 只用于诊断，不作为正式评估结果来源。

写文件采用临时文件加原子替换，避免电脑端读取到半个 JSON。

### 7.5 隔离人工操作

Eval 环境有效期间，TestApp 会隔离人工文字、语音、会话切换和相关 UI/TTS 行为，避免同一个 App 的人工操作污染评估过程。Eval 结束后恢复原有调试功能。

## 8. 一条测试案例是怎样运行的

一条典型车控案例按以下顺序执行：

1. 电脑端从 Dataset 读取案例并生成 correlationId。
2. TestApp 向 AIAgent 获取独占 Eval 环境。
3. 重置车辆状态并应用案例要求的初始状态。
4. 创建或切换到独立评估会话。
5. 读取请求前车辆状态快照。
6. TestApp 通过正式 AIDL 发送真实 TEXT AgentRequest。
7. AIAgent 完成 Context、LLM、Tool 和 Safety 流程。
8. TestApp 接收真实 AgentResponse。
9. 再次读取车辆状态，形成前后对比。
10. TestApp 将完整 EvalResult 原子落盘。
11. 电脑端读取结果，并按 requestId/clientMessageId 查询 Phoenix Trace。
12. 电脑端执行确定性检查、Hard Gate 和配置化 LLM Judge。
13. 保存本次 Trial 证据，并生成 Run 汇总与版本比较报告。
14. 清理临时会话并释放 Eval 环境。

## 9. 这套 Eval 主要评估什么

初版系统重点覆盖基础 Agent 能力，而不是追求一次建设完整评测平台。

### 9.1 基础问答能力

- 是否回答用户问题；
- 是否答非所问；
- 表达是否清晰；
- 是否出现明显错误或异常终态。

### 9.2 Tool 使用能力

- 是否选择正确工具；
- 工具参数是否正确；
- 是否发生漏调用、错调用或重复调用；
- 工具执行结果是否正确回到模型循环。

### 9.3 车辆状态能力

- 初始车辆状态是否符合案例要求；
- Tool 执行后状态是否按预期变化；
- 被拒绝或失败的操作是否保持状态不变；
- 多条案例之间是否发生状态污染。

### 9.4 安全能力

- 高风险动作是否被拒绝或要求二次确认；
- 确认前是否禁止执行；
- 确认后是否只执行目标动作；
- 安全失败是否能成为 Hard Gate。

### 9.5 运行流程完整性

- Trace 是否只有一个正确根请求；
- Context、LLM、Tool、Safety 和响应分发证据是否完整；
- AgentResponse、状态快照和 Trace 是否能够稳定关联；
- 超时、取消、断连和异常是否具有确定终态。

## 10. 系统设计特点

### 10.1 先完成最小闭环，再增加自动化

系统先通过 Fixture 和半自动方式验证协议、结果和评分，再在相同入口上增加 ADB 自动运行。自动化不会建立在未经验证的链路上。

### 10.2 三类事实各自权威

- AgentResponse 是用户最终收到结果的权威来源；
- VehicleStateSnapshot 是车辆状态的权威来源；
- Trace 是运行过程证据的权威来源。

系统不会用 Trace 文本代替 AgentResponse，也不会仅凭模型回答推测车辆状态。

### 10.3 共享协议统一三端

电脑端 Schema 是跨项目协议标准，两个 Android App 是协议实现方。统一协议用于避免三个项目各自定义字段，导致结果无法互相解析。

### 10.4 确定性规则优先，LLM Judge 补充

可以用代码明确判断的事实由确定性规则负责；只有自然语言质量等开放问题交给 Judge。这样能够降低模型评分波动和成本。

### 10.5 可复现和可追溯

Dataset、配置、版本指纹、结果、Trace 关联和报告共同保存，使一次评估可以被复查，也能用于后续版本比较。

### 10.6 保留升级空间但控制 Demo 边界

初版只建设本地单机、单设备、基础 Agent 能力评估，不引入 Web 平台、数据库、CI、多设备并行或分布式调度。但 Dataset、Executor、Grader、Judge 和 Report 均保留后续扩展接口。

## 11. 本轮计划最终定义了一个什么样的 Eval 系统

三份计划共同定义的不是一个简单的“问一句、看回答”的测试脚本，而是一套轻量、可扩展、证据驱动的 Agent 评估闭环：

- 电脑端负责案例、执行、评分和报告；
- TestApp 负责设备桥接和结果采集；
- AIAgent 提供真实业务链路、可控环境和 Trace 证据；
- 每条案例从确定状态开始，以结构化结果结束；
- 结果可以通过规则、状态和 Trace 交叉验证；
- 不同 Agent 版本可以使用同一 Dataset 重复评估和比较。

从项目管理角度看，这套系统的核心价值是把 Agent 开发从“依赖人工体验”推进到“具备标准案例、运行证据、质量门槛和版本对比”的可持续迭代方式，并为后续 RAG、视觉问答和更多车载能力建立统一的评估基础。
